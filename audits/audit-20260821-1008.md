**Finding C1 is withdrawn.** I verified it against source call sites and did not check
the linked artifact. Symbol table of the accepted product ELF
(`id-e8720d58595d9a62/obj/sm64-saturn-sourceboot-e2.elf`, 8,241 symbols, read with


`_vdp2_sync_wait` resolves, so the query is sound; the rest of the `vdp1_sync` family
links; **`_vdp1_sync_wait` is not in the binary at all.** No reachable caller exists, so
the unbounded fence is not in the shipped product. `demo_upload_vdp1_dual` has no
callers and `sm64_saturn_vdp1_backend_upload` is `static inline` and evidently uncalled
on the product path — had either been reachable, the libyaul symbol would have linked.

**Consequence for C2:** the exit-criterion rewrite stands as a documentation
observation, but its force is much reduced. If the fence is unreachable, then
"defer before reaching it" is not a substitute for bounding the wait — it is the
correct mechanism, and the re-scope was right. The summary's "no unbounded spin" is
**accurate for the accepted artifact**. What remains worth doing is recording the
criterion change and its rationale, not reopening W0.

**Method note for future audits of this codebase:** source-level reachability is not
evidence here. `--gc-sections` removes uncalled statics, and this project has hit that
exact trap before — T2.16 found the four "blocking fork-joins" were dead code because
`_sm64_saturn_dual_worker_run` was absent from the product ELF for the same reason.
**Check the symbol table before calling a source-visible path live.** I knew that
precedent and did not apply it.

## Findings

### Critical

**C1. `vdp1_sync_wait()` is still unbounded. The hang path W0 was created to remove is
still present.**

Evidence — both call sites are untouched by any W0 commit:

- `src/port/saturn/gfx/saturn_demo_render.c:3996` — `vdp1_sync_wait();` immediately
  followed by `assert(!vdp1_sync_busy());` in `demo_upload_vdp1_dual()`.
- `src/port/saturn/gfx/saturn_vdp1_backend.h:480` — `vdp1_sync_wait();` in
  `sm64_saturn_vdp1_backend_upload()`.

`git show --stat da41248f` ("fix(saturn): defer busy VDP1 overwrites") touches
`sourceboot/main.c`, `saturn_prenotify_profile.h`, and capture tooling. **It touches
neither file containing the fence.**

The plan's own W0 rationale still reads, unedited and in the present tense:

> **Why:** `vdp1_sync_wait()` has **no deadline** … This is the hang path in the build
> awaiting observation.

…while the same section is now marked `**Status:** complete; owner-accepted`. A section
whose stated problem is verbatim unsolved should not be marked complete.

This matters more than a documentation slip because of C2 and I2 below: the new deferral
mechanism has never been observed to execute, so in every measured run **the unbounded
fence is still the operative path**.

**C2. The delivered mechanism is not the one the risk analysis called for, and the exit
criterion was rewritten to match the delivery.**

The exit criterion originally read:

> **Exit:** the fence has a bounded wait with a defined failure behaviour that degrades
> rather than hangs

It now reads:

> **Exit:** the fence performs one busy observation and immediately defers the exact
> ready generation …

These are different goals. Deferring *before* reaching a blocking wait is a defensible
design — arguably better than bounding the wait — but the change was made to the
acceptance criterion rather than declared as a re-scope, and the superseded criterion is
not recorded anywhere in the section. As written, the document now contains a **Why**
describing an unsolved problem and an **Exit** describing a different, solved one, with
nothing connecting them.

The summary's phrase "no unbounded spin" is true of the new deferral path and **false of
the pre-existing fence that remains in the binary**.

### Important

**I1. The first live observation failed, and the reported number comes from a retry with a
modified observer. The summary omits this.**

The summary states flatly: "normal live capture recorded 30 presentation events, 6.69 FPS
mean / 6.0 low, with no queue/coherency faults."

The evidence ledger records (`w0-vdp1-overwrite-fence.md:35`):

> attempt 1 reached generation 50 with coherent queues but stopped on an unstable cadence
> seqlock

Commit `facb9db7` then changed `capture_sourceboot_throughput.py` (91 lines) to retry, and
the reported figure comes from that rerun. **The evidence file is honest about this; the
summary is not.** The measurement is still credible — the change is tool-only and bounded
(see W1 under "done well") — but a reader of the summary alone would not know the
instrument was modified between the failed and successful observation.

**I2. The deferral path is never demonstrated to execute — so the added safety code is
unexercised at runtime.**

The summary lists this under "what it did not do," which is honest. The ledger is explicit
(`w0-vdp1-overwrite-fence.md:35`):

> No diagnostic capture: normal observation did not classify a busy deferral

Consequence: W0 adds a mechanism and its telemetry, both verified only by host contract
tests, and ships a candidate in which — so far as any live run shows — the mechanism never
ran. Combined with C1, the net runtime change to the hang risk is **unproven in either
direction**.

**I3. Cadence regressed slightly and the direction is unstated.**

6.6923 mean against the `id-c0352f297034f653` baseline of 6.7181 = **−0.38%**. The summary
says "did not improve FPS materially," which is accurate but omits that the movement is
negative. Almost certainly noise — 1% low is unchanged at 6.0 — but "did not improve" reads
as "held flat."

## Recommended next actions

1. **Reconcile W0's Why with its Exit, or reopen W0.** Either bound `vdp1_sync_wait()` as
   originally specified, or amend the **Why** to state that the fence is deliberately left
   unbounded because the deferral makes it unreachable — and then *prove* unreachability,
   which currently rests on a path that has never executed (I2). Right now the plan asserts
   both that the hang path exists and that the workstream addressing it is complete.
2. **Record the exit-criterion change explicitly**, with the superseded text and the reason.
   A rewritten acceptance criterion is a legitimate decision and an invisible one is not.
3. **Force the deferral path to execute at least once** — a diagnostic build that injects a
   busy VDP1, or a synthetic hold — so the mechanism and its telemetry are observed rather
   than only contract-tested. Until then "busy safe" is a design claim, not a result.
4. **Correct the `id-c0352f297034f653` provenance line** to "launched, never
   owner-adjudicated" (M2).
5. **State the −0.38% cadence direction** in the ledger so the next comparison starts from a
   true baseline (I3).
6. Before starting W1, note that the plan's own ordering rule is "W0 before anything
   (correctness)." If C1 stands, that precondition is not yet met on its original terms.
