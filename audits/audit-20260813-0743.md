   `.tmp-normal-bob-replay-visible.png` is a 320x224 image with visibly malformed
   BOB terrain, incorrect depth/occlusion presentation, a disproportionately large
   Mario, and no recognisable, textured Bob-omb witness. This fails the owner’s
   stated manual acceptance conditions even though the simulation and actor queue
   are running. It must not be described as a working demo.

2. **The current normal replay has no audio implementation.** The active replay

   (`.tmp-normal-bob-replay-profile.json:1`). The source Makefile chooses
   `source_audio_stub.c` when that flag is off (`src/port/saturn/sourceboot/Makefile:465-470`),
   and its `play_sound`, `play_music`, and initialization functions are empty
   (`src/port/saturn/sourceboot/source_audio_stub.c:15-68`). There is no music or
   game-triggered SFX path in this candidate.

### Important

1. **The generic actor path is real, but only a functional—not visual—proof.**
   The replay records normal `bhvBobomb` identity `(family_id=7, model_id=188)` at
   `.tmp-normal-bob-replay.json:20535-20558`; it is `active=1`,
   `render_active=1`, generates 68 output records, and has no render-job failure.
   This is good evidence that the object is not injected or substituted. It is not
   proof that its material, scale, depth order, or texture UVs are correct on VDP1.

2. **The green tests do not test the failing visual property.**
   `tools/saturn/test_render_snapshot_source.py` passes, and the painter-chain
   binary passes, but both are structural/source-level checks. The former asserts
   that Mario’s texture-detail command is configured to use a fixed Gouraud table

   construction. Neither runs Ymir nor judges the framebuffer. The implementation
   does contain the expected fixed-table code (`saturn_demo_render.c:3815-3842`),
   yet the captured screen is still wrong. That is a clear test-to-acceptance gap.

3. **The active visual experiment is not a clean, reproducible baseline.**
   `git status` shows 91 tracked modified files, and `git diff --stat` totals
   3,898 insertions / 753 deletions. The sourceboot candidate
   `id-f49c32ac69e5385a` is identity-bound, but the replay JSON itself carries no
   identity field and the worktree has a substantial concurrent renderer/runtime
   diff. The screenshot can guide diagnosis; it cannot certify that the present
   worktree, a future build, and the captured target bytes are identical.

4. **The likely visual fault is still unisolated.** The transform currently clamps
   projected coordinates to the full VDP1 range `[-1024, 1023]`
   (`saturn_demo_render.c:102-103`, `saturn_ir_transform.c:55-58`), not the
   320x224 viewport. The terrain and actor lowerers then enter a shared 64-bin
   painter chain (`saturn_demo_render.c:3550-3593`, `4615-4617`). This may be
   correct for VDP1 offscreen primitives, so it is not a proven bug; it is the
   next discriminating hypothesis. Do not redesign clipping, sorting, or material
   formats before a target capture proves which part of this path produces the
   malformed terrain.
