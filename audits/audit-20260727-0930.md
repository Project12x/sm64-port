**2. The 100,000-case differential samples vertex coordinates from `int16` range only.**
`runtime_contract_test.c:394` draws `v[i] = (float)(int16_t)(random >> 16)`.
Under `GBI_FLOATS`, `Vtx_t.ob` is `float[3]`, so real coordinates are not

yields identical products. The `v` range is therefore incidental. Worth noting
only because the test's own comment says "real Vtx coordinate range", which is
narrower than what `GBI_FLOATS` actually permits.

## Correctness analysis

The invalidation design is the main risk in a cache like this, and it is
handled correctly:

- `mp_float` is refreshed **inside** the same `if (stack->mp_dirty)` block that
  recomposes `mp`, before `mp_dirty` is cleared (`saturn_matrix.h:300-308`). It
  therefore cannot go stale independently of `mp` — there is no second dirty
  flag to fall out of sync.
- The consumer captures `&frontend->matrix_stack.mp_float` at
  `frontend.c:292-293`, **after** the `sm64_saturn_matrix_stack_mp()` call at
  `:290-291` that performs the refresh. Ordering is correct.
- `grep -rn mp_float` shows **no reader anywhere** that bypasses
  `sm64_saturn_matrix_stack_mp()`. There is no path to a stale read.

The bit-exactness claim holds under inspection:

- `sm64_saturn_q16_to_float` special-cases `q == 0` (`kernels.h:165-167`) — the
  case where naive exponent manipulation would produce garbage, and the one an
  all-random test would almost never hit (~0.009% over 400,000 draws). It is
  additionally covered by the identity-projection assertions at `:361-367`,
  which decode a matrix containing real zeros.
- For non-zero `int32`, `(float)q` has biased exponent in 127–158, so
  `exponent - 16` lands in 111–142 — no denormal, no overflow. Division by 2^16
  in IEEE-754 is an exact exponent decrement, so the bit manipulation is
  equivalent to `/ 65536.0f` by construction, not merely empirically.

HWRAM: `___end = 0x060e1024` → **126,940 bytes free**, versus 126,972 before.
32 bytes consumed (the cache is 48 bytes but sits inside an existing struct).
Comfortably clear of the 4,096-byte linker floor and still above BOB's
87,018-byte staging requirement.

## What was done well

- **The cache is placed where it cannot desynchronise.** Putting the refresh
  inside the existing `mp_dirty` block, rather than adding a parallel dirty
  flag, eliminates the entire class of stale-cache bug by construction. The
  code comment says exactly this and is accurate.
- **The laziness test is the good kind.** Poisoning `mp_float.x[0]` and
  asserting it *survives* a clean read (`:373-375`) directly observes the
  optimization rather than its side effects, and would kill an
  unconditional-refresh mutation. Then re-dirtying and asserting repair covers
  the other direction.
- **Bit-exactness was chosen over a tolerance.** This matches the handoff's
  guidance that this increment is available without a behavioural gate, and it
  is a materially stronger bar than the Q16.16 conversion will be able to meet.
- **The measurement is honest and reproducible.** Both anchors were committed,
  and my independent decode reproduced every figure including the exact render
  counts. The claimed quantum is correct rather than decorative.
- **Scope discipline.** No engine-tree edits, no vendored code, no opportunistic
  refactoring. The diff is 148 lines across three files and does one thing.
- **The stale comment was updated.** The old comment claimed the per-corner
  float math was "fine for a first, correctness-focused pass"; it was rewritten
  to describe what the code now does. Easy to skip, frequently skipped.
