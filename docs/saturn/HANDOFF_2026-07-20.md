## What is verified

### 1. Source loop ownership is real

The following production call chain is linked in `sourceboot`:

```text
original thread5_game_loop()
  -> original game_loop_one_iteration()
  -> original level_script_execute()
  -> direct original level_bob_entry
  -> original display_and_vsync()
  -> target exec_display_list(struct SPTask *)
  -> saturn_fast3d_frontend
```

Relevant files:

- `src/port/saturn/sourceboot/main.c` — target entry and one source frame per
  iteration after source bootstrap.
- `src/port/saturn/sourceboot/source_entry.c` — bounded selection of the
  original `level_bob_entry`; not a handmade level.
- `src/game/game_init.c` — retains source frame sequencing and target service
  seams under `TARGET_SATURN`.
- `src/port/saturn/runtime/saturn_source_runtime.c` — public
  `exec_display_list()` dispatcher and Saturn controller/VBlank services.
- `src/port/saturn/gfx/saturn_fast3d_frontend.c` — bounded Fast3D task walker.

The existing front end follows display-list control flow and counts source
workload categories. It does **not yet** interpret matrix/vertex/triangle
commands into VDP1 commands. Therefore it proves dispatch, not visual output.

### 2. Direct source data fits the 4 MiB cartridge

`sourceboot` now emits two linked payloads:

| File | VMA | Size | Contents |
| --- | ---: | ---: | --- |
| `A.BIN` | `0x06004000` | 1,022,564 bytes | Yaul bootstrap, platform seam, source-loop code, CDFS/cart loader, mutable frame state |
| `SOURCE.DAT` | `0x22400000` | 1,694,864 bytes | Immutable original source tables, display lists, textures, animation/model data |

`SOURCE.DAT` SHA-256:

```text
cd4e0d0b6791f7288b570e2d7cddfdcc1ad95a130577c9c6cd0979361baedefd
```

The bank is below the 4 MiB / 4,194,304-byte limit. The target loader copies
the CDFS file through a 16 KiB HWRAM staging buffer to the DRAM cart with
16-bit bus-safe stores, before original source data may be dereferenced.

Key files:

- `src/port/saturn/sourceboot/sourceboot-cart.x` — Yaul linker-layout
  adaptation; places source read-only data at `0x22400000`.
- `src/port/saturn/sourceboot/source_cart.c` — cartridge detection, CDFS load,
  exact-size check, and target probe.
- `src/port/saturn/sourceboot/Makefile` — emits `SOURCE.DAT`, adds it to the
  ISO, and verifies the VMA/entry point.

More detail and provenance: [E2 4 MiB cart-bank evidence](evidence/e2-sourceboot-cart-bank-2026-07-19.md).

## Mandatory acceptance gates

### Cart bank gate — open

The cart-enabled GUI/debugger must expose a probe with all of the following:

| Field | Required value |
| --- | ---: |
| magic | `0x53434152` |
| stage | `5` (`READY`) |
| status | `0` (`OK`) |
| cart id | Yaul `DRAM_CART_ID_4MIB` / `0x5C` |
| cart size | `4,194,304` bytes |
| expected size | `1,694,864` bytes for the current build |
| copied size | exactly `1,694,864` bytes |

After that evidence exists, add a content hash or package header validation to
the loader. The current exact-size check is necessary packaging validation but
is not an integrity check.

### Source-frame visual gate — open

The front end must lower a real submitted Fast3D task through the shared VDP1
path. A valid first capture must show actual source-owned geometry, not a
reconstructed Castle/Mario viewer and not a fake/mock image. It must identify
the build, camera/state, command count, overflow state, and the active
cart-loader probe result.

The first pass may be untextured, provided it is explicitly labelled as such.
Texture, lighting, clipping, and painter ordering are global renderer work;
none may become a Bob-specific exception.

### Source-controlled movement gate — open

Use the inherited controller path to record a deterministic idle/run/jump
route on a PC reference run, then require matching Mario action, position,
camera mode, and final state on Saturn. A screenshot or response to a manual
input alone does not prove source-owned locomotion.

### Performance gate — open

The desired gameplay target is 15–20 FPS with the 4 MiB cartridge. Existing
Castle-harness Ymir measurements around 9.95 loop FPS are diagnostic history,
not sourceboot performance and not an acceptable target. Do not optimize
viewer-only code and call it source-port progress.

## Known constraints and traps

- `SOURCE.DAT` uses its final `0x22400000` pointer addresses. Never move
  source data back into a temporary copy or dereference it before the cart
  loader succeeds.
- `sourceboot` has an explicit direct-level closure. Menu, Castle Grounds, and
  TTC `leveldata.c` files are retained only because the original global source
  data references them. Do not remove them casually or replace them with
  copied level-local tables.
- Collision catalog generation deliberately excludes `bob`, `castle_grounds`,
  and `ttc` because their direct source objects are linked; this avoids
  duplicate symbols.
- `capture_hwtest.py`'s normal telemetry address (`0x06030000`) is not the
  source-cart probe. Always resolve the `g_sm64_saturn_source_cart_probe`
  symbol from the current build map before probing.
- The GUI profile supports the 4 MiB cart; headless does not. Do not turn the
  headless failure control into a claim that Ymir lacks RAM-cart support.
- The user-supplied BIOS and ROM remain outside Git. Do not commit them,
  extracted ROM headers, `build/`, or generated disc contents.
- There is a large historical evidence/screenshots backlog already untracked.
  Preserve it and stage exact named files only. The authoritative visual
  timeline is `docs/saturn/evidence/TIMELINE.md`; embed only actual captured
  target screenshots there.
- No retail-hardware test has occurred. Ymir evidence is emulator evidence;
  real hardware remains the final authority for the DRAM cart and VDP timing.
