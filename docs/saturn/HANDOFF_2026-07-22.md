## MAJOR UPDATE (2026-07-22, later the same day): free-roam gameplay reached; the Boo-hang finding further down this document is retracted

Everything below this box (the capacity-increase work and the "Critical: Boo-behavior
CPU hang" section) is **preserved as an accurate historical record of that part of the
day**, but two things changed after it was written and must be read first:

1. **The "Boo-behavior CPU hang" is not a real hang.** It was a `capture_hwtest.py`
   bug: Ymir's headless debug service hard-caps a single `exec.run_for` call at 3,600
   frames and returns a JSON-RPC error above that, but the script never checked that
   specific response. Every request for more than 3,600 frames was silently rejected,
   so the emulator never advanced past whatever depth preceded it, and every later read
   faithfully reported that same frozen-looking-but-not-frozen state. Fixed and
   committed (`c28980a`, chunks every call to <=3,600 and validates each chunk). There
   is no CPU hang, no memory corruption at that specific point, and no Boo-related
   bug. Full retraction: [[project-saturn-port-boo-hang]] memory file, or read
   `c28980a`'s commit message.
2. **The real bottleneck was found, and the game now reaches genuine free-roam
   gameplay for the first time in this project's history.** Six commits
   (`7c60d60`, `e0a0a21`, `3c89bd1`, `2574342`, `621ff61`, `1f76b66`) fixed a missing
   Mario/save-file init call and four downstream gaps it exposed (level identity, act
   number, controller input, a mis-staged intro cutscene). Mario now idles at BOB's
   spawn with working input and a running camera, verified live through ~400 game
   frames with no crash. **The screen is still blank** — a separate, real bug (a
   corrupted `G_MTX` matrix) is the one remaining blocker to visible pixels. Full
   detail in the new section below, "Free-roam gameplay reached; matrix-corruption
   bug is the last blocker."
3. **The corrupted matrix was traced past `gGfxPool` entirely, into unmodified
   SM64 engine code.** The corruption is not a `gGfxPool` allocator
   collision — it is already present in `gMatStack[1]` (SM64's own float
   matrix stack, `src/game/rendering_graph_node.c`), freshly produced every
   frame by `mtxf_lookat`/`mtxf_mul` (`src/engine/math_util.c`) from the live
   camera's position/focus. Those inputs were directly read and are
   provably not degenerate (confirmed both from `gCamera` and from
   `gLakituState`, the struct that actually feeds the calculation, and by
   exhaustively simulating `mtxf_lookat`'s exact formula against all 65,536
   possible roll values with the real captured data — zero degenerate
   cases). Every other candidate mechanism tested (never-initialized Lakitu
   interpolation state, a sibling geo-node reusing the same stack slot,
   `mtxf_mul`'s own logic) was also directly ruled out.
4. **A host-vs-target differential test settled the remaining question:
   this is SH-2-target-specific, not an algorithm bug.** The real,
   unmodified `math_util.c` was compiled with the host compiler and fed the
   exact real captured camera pos/focus, swept across all 65,536 roll
   values — using the real `gSineTable`/`gCosineTable` data, not an
   approximation. Zero anomalies of any kind on host; every result is sane.
   The same real inputs, the same real unmodified engine code, produce a
   completely different result on the SH-2 target. This exonerates the
   algorithm and points at the SH-2 cross-compiler's codegen or soft-float
   library for this exact input pattern. Per explicit instruction,
   disassembly forensics of the compiled machine code is a separate, larger
   decision, not started here. Full detail in
   [`evidence/e2-sourceboot-gmatstack-corruption-2026-07-22.md`](evidence/e2-sourceboot-gmatstack-corruption-2026-07-22.md).

## Outcome: no visible or counter-level change at this boot depth

Per the plan's Task 5 Step 1 outcome (b): **no TIMELINE.md success entry was
written.** The capacity increase is real, tested, and correct at the
capacity-rejection level (`rej_cmd_cap=0` and no VDP1-arena rejects in either
capture — the resolve buffer and command arena were never what filtered
triangles out), but it produced zero effect at frame 47 of this boot,
because raising a downstream capacity ceiling cannot change anything when
the actual constraint is upstream of it. Out of 573 transformed triangles at
this frame:

- **447 are rejected by `rej_near_far`**, and of those, 293 fail the strict
  `w <= 0.0f` reject (`profile->reject_w_nonpositive`, clip-space w
  non-positive — behind the camera or a degenerate perspective divide) and
  154 fail `z_far` (beyond `SM64_SATURN_FAR_DEPTH = 16384`).
- **107 are rejected by `rej_backface`.**
- **0 are rejected by `rej_degenerate`, `rej_vtx_range`, or `rej_cmd_cap`.**
- **18 survive** all filters into `tri_emitted` — matching this
  project's independently-documented "~18/frame" figure — and **none of
  those 18 reach `tri_vdp1_emitted`** in either capture (it is 0 both
  before and after), which is the direct, verified reason the two frames
  are pixel-identical: nothing was submitted to VDP1 in this specific frame
  regardless of either capacity ceiling.

**Caveat: the six terminal buckets above sum to 572, one short of the 573
`triangles_transformed` total** (447 + 107 + 0 + 0 + 0 + 18 = 572, decoded
directly from both JSON reports' `probe_window` bytes against the real
`sm64_saturn_fast3d_profile_t` layout, not just this document's
transcription). `sm64_saturn_fast3d_resolve_triangle()`
(`src/port/saturn/gfx/saturn_fast3d_frontend.c:155-412`) increments
`triangles_transformed` exactly once at entry (line 204, the sole increment
site) and every code path terminates through exactly one of six
mutually-exclusive counters (`reject_vertex_range`, `reject_near_far`,
`reject_backface`, `reject_degenerate`, `reject_command_capacity`,
`triangles_emitted`), so by construction the six should sum to the total —
they do not, by exactly one triangle, in both the before and after capture
(which are otherwise byte-identical, including `frame_serial=47`). The most
likely explanation is a probe read landing mid-frame: the 573rd triangle's
`triangles_transformed++` had already been recorded at the instant
`mem.peek` sampled live SH-2 RAM, but that same triangle's terminal
reject/emit counter had not yet been written — the same class of
read-timing artifact this project's own `frame_serial` sanity-gate
methodology exists to catch, just a 1-triangle-scale instance of it rather
than the multi-order-of-magnitude misread that gate was built for. This
does not change any conclusion above (the 447/107/18 figures and the
`tri_vdp1_emitted=0` result are unaffected), but the 573 total should be
read as accounted for to within one triangle, not fully closed.

This is not a capacity problem. Raising `SM64_SATURN_FAST3D_MAX_RESOLVED_TRIANGLES`
and `SOURCEBOOT_VDP1_COMMAND_CAPACITY` was necessary infrastructure (real
Bob-omb frames run 1,365-1,431 triangles, and 192/512 would have capped hard
against that once the true bottleneck below is fixed), but at frame 47 the
resolve stage never comes close to either the old or new ceiling — it discards
554 of 573 triangles before capacity is ever checked.

3. **`rej_backface` (107 of 573).** Lower priority — backface culling

## Free-roam gameplay reached; matrix-corruption bug is the last blocker

This section was written well after the sections above it, once the Boo-hang
retraction and a long investigation chain had played out. Read it as the
current state of the project, superseding the "Next implementation" and
"Critical: Boo-behavior CPU hang" sections above (the latter is retracted, not
deleted — its own header now says so).

### How we got from "no visible change" to "genuine free-roam gameplay"

The capacity work above was real and correctly executed, but its own
diagnostic evidence (`rej_near_far=447`, `rej_backface=107`, only 18 of 573
triangles surviving) pointed at something upstream of capacity. Investigating
that chain, in order:

1. **The `capture_hwtest.py` chunking bug was found and fixed** (`c28980a`,
   see the MAJOR UPDATE box) while re-verifying an implausible diagnostic
   read — this is what retracted the Boo-hang finding.
2. **The real rejection root cause was traced to a Q16.16 matrix-composition
   overflow**: `mp[2][3] == INT32_MIN` recurred bit-for-bit across independent
   rebuilds. Traced back through the matrix stack (`41baf5b`) to a single
   corrupted source float feeding `top->m[2][2]` — and that float's raw bits,
   reinterpreted as a big-endian `uint32`, matched the `G_SETOTHERMODE_L`
   opcode byte pattern almost exactly (`0xE200001C`). The "matrix" data a
   `G_MTX` decode consumed was the literal bytes of a different, later
   Fast3D command (`eb5bbbf`).
3. **That, in turn, led to a real, deterministic CPU crash being found and
   fixed.** Register-level bisection caught the SH-2 permanently frozen
   (`PC=0x2`, all interrupts masked) at the exact same real-game-frame in
   every single capture, regardless of depth. Root cause:
   `gMarioState->animList` was NULL, because `init_mario_from_save_file()` —
   which the retail master script always calls once before any level script
   runs — was never invoked (this port's boot skips straight into
   `level_bob_entry`, never executing the castle-grounds flow that normally
   calls it). The NULL deref cascaded into a garbage ~1.2 GB `memcpy` the
   moment Mario's animation system first ran (jumping out of the intro
   pipe). Fixed in `7c60d60`: call `lvl_init_from_save_file()` via the same
   level-script `CALL` mechanism already in use, verified safe first (its
   save-file dependencies only touch a zero-initialized static buffer, never
   real EEPROM hardware).
4. **Fixing that crash exposed a new, non-crashing stall** (Mario correctly
   waiting on a camera/cutscene handshake that never completed) — which a
   systematic multi-agent audit of "what does the retail castle-grounds boot
   flow set up that this direct-into-level boot skips" (7 gaps confirmed, 0
   refuted) explained was not actually the handshake itself, but four other
   missing pieces compounding:
   - **Boot call order** (`3c89bd1`): `lvl_init_from_save_file` needs to run
     *before* `lvl_set_current_level`, not after — the previous order left
     the whole session running with the wrong level identity
     (`gCurrLevelArea=0x11` instead of `0x91`), silently disabling the
     camera's real `AREA_BOB` handling.
   - **Act number never set** (`2574342`): `gCurrActNum=0` made a level-script
     computation shift by -1 (UB, yields 0 on SH-2), so only "all acts"
     objects were spawning. Fixed by setting act 1 through the same
     script-register path the retail act-selector uses.
   - **No controller input at all** (`621ff61`): sourceboot never called
     `smpc_peripheral_init()` or serviced per-frame intback, unlike both
     working sibling targets. Wired in, verified live with an actual button
     press reaching `gControllers[0].buttonDown`.
   - **Intro cutscene staged against the wrong level** (`1f76b66`): retail
     only ever runs the no-save-file Peach intro in castle grounds; booting
     straight into BOB with no save file mis-staged it. Fixed the retail way
     — mark the save file as existing before init, so Mario just spawns
     normally with no intro at all.

### The one remaining blocker: screen is still blank

The screen is a uniform near-white frame even in the free-roam state, and the
counters are structurally the same as during the (now-removed) intro
cutscene: ~96% of transformed triangles rejected, `tri_vdp1_emitted=0`.
Reaching free-roam **disproved the leading theory for the corruption's
trigger**: it was suspected to be sustained HUD-dialog rendering pressure
against SM64's shared `gGfxPool` (a fixed 51,200-byte buffer where the Gfx
command stream grows forward while `alloc_display_list` allocations, used for
matrices/vertices/text, grow backward from the other end, with no bounds
check preventing an eventual collision) — but with the intro/dialog now gone
entirely, the corruption profile is unchanged. Live measurement in the
free-roam state (12 samples across 23 game frames) found the two fronts
39.8 KiB apart, nowhere near colliding (`d244950`'s commit message has the
exact numbers). The pool-collision theory is dead.

**Update: that follow-up capture has now been run.** Full detail in
[`evidence/e2-sourceboot-bad-mtx-pointer-2026-07-22.md`](evidence/e2-sourceboot-bad-mtx-pointer-2026-07-22.md).
Summary: the corrupted `G_MTX` command's `w1` pointer (`0x0608f970`) is
**not garbage** — it falls squarely inside `gGfxPools`' backing array
(`0x06083980` + 47,600 bytes, comfortably inside one 51,200-byte bank).
Reading memory at that address directly shows a mix of plausible small
floats interleaved with the same `0xE200001C` (`G_SETOTHERMODE_L`-shaped)
corruption signature and several real HWRAM-address-looking pointer words —
consistent with an `Mtx` that was legitimately allocated from the pool, but
partially overwritten by different content before this session's Fast3D
frontend decoded it.

Two plausible mechanisms were directly ruled out: retail's per-frame pool
reset (`select_gfx_pool()`) **is** already being called correctly every
frame via the exact code path this port already runs
(`game_init.c:789`) — not another missing-init-call bug like the five
fixed earlier today; and this port's `exec_display_list()`
(`saturn_source_runtime.c:100`) decodes the display list **synchronously**,
same-frame, ruling out a stale pointer surviving across a frame boundary.
`alloc_display_list()` itself (`memory.c:750`, the variant this build
compiles) was read and is a standard, unmodified bump-allocator with no
obvious defect visible from source alone.

**Update: the mechanism has been found, and it is not `gGfxPool`.** Full
detail in
[`evidence/e2-sourceboot-gmatstack-corruption-2026-07-22.md`](evidence/e2-sourceboot-gmatstack-corruption-2026-07-22.md).
A direct read of `gMatStack` (SM64's own float matrix stack,
`src/game/rendering_graph_node.c:40`) found the identical corruption
signature already present at entry index 1 — **before** `guMtxF2L`'s memcpy
ever copies it into `gGfxPools`. This closes the loop with this session's
very first finding (Thread 1's `decoded.m[2][2]==INT32_MIN`): they were
always the same bug. `gGfxPool`'s allocator, `select_gfx_pool`'s per-frame
reset, and `sizeof(Mtx)`/`GBI_FLOATS` are all fully exonerated — the
corruption predates all of them.

`gMatStack[0]` is confirmed a clean identity matrix every frame
(`geo_process_root` sets it unconditionally) and `gMatStack[1]` is freshly
computed every frame by `geo_process_camera` from a **local** stack
variable (`mtxf_lookat`'s output) — there is no code path for stale
cross-frame data here. Four candidate mechanisms for *why* the freshly-
computed value is bad were tested and ruled out with direct live evidence:
degenerate camera pos/focus feeding `mtxf_lookat` (checked via both
`gCamera` and `gLakituState` — the field that actually feeds the
calculation — and via an exhaustive Python re-simulation of `mtxf_lookat`'s
exact formula against all 65,536 possible roll values with the real
captured data: zero degenerate cases), never-initialized Lakitu
interpolation speeds freezing the camera at the origin, a sibling geo-node
in Bob-omb's own geo layout reusing the same stack slot later in the frame,
and a defect in `mtxf_mul`'s own multiply-accumulate logic. A direct
re-verification capture confirmed the corruption is byte-for-byte
reproducible (not a one-time fluke) and that `gMatStackIndex` correctly
unwinds back to 0 (the push/pop bookkeeping itself is not broken).

**A host-vs-target differential test then settled which of the two
remaining candidates is real.** The real, unmodified `math_util.c` was
compiled with the host compiler (`tools/saturn/mtxf_lookat_host_diff_test.c`,
`make -f Makefile.saturn.mk verify-mtxf-lookat-host-diff`) and fed the
exact real captured camera pos/focus, swept across all 65,536 possible
roll values, using the real `gSineTable`/`gCosineTable` data (not an
approximation). Result: **zero anomalies of any kind** — every one of the
65,536 results is a sane, small-magnitude value. The same real inputs, the

## Critical: Boo-behavior CPU hang discovered during this effort — RETRACTED, see the MAJOR UPDATE box at the top of this document

**This entire section is preserved for historical accuracy but is WRONG.**
There is no CPU hang. The root cause was a `capture_hwtest.py` bug (Ymir caps
`exec.run_for` at 3,600 frames/call; the script never checked for that
specific error, so deeper requests were silently no-ops), fixed in `c28980a`.
Do not act on anything in this section without reading the retraction above
first.

Investigating an earlier implausible diagnostic read (`frame_serial` in the
tens of millions for a run that can only have executed a few hundred real
game frames) found a genuine SH-2 CPU hang, not a tooling bug:

- **A full SH-2 register freeze occurs somewhere between `--post-poke-frames
  3600` and `3800`** on this exact boot (240 BIOS frames, USA BIOS input
  macro, `dram_cart`, the `e2-bob` sourceboot target). Every general-purpose
  register, `PC`, `PR`, `SR`, `GBR`, `VBR`, `MACH`, and `MACL` were observed
  bit-for-bit identical across a 3,200-emulated-frame span once the hang
  begins — this is a true CPU freeze, not merely a static scene.
- **`PC` is stuck inside `_boo_update_during_death`, in the middle of
  evaluating `_cur_obj_has_behavior(&_bhvBoo)`.**
- Cache-coherency, stale-probe-address, and struct-layout theories were all
  tested and ruled out as explanations for the implausible early reading —
  it is a real, reproducible hang in the emulated program, confirmed by
  deliberately capturing at `3600` (plausible, live, `frame_serial=47`) and
  `14000` (frozen) and finding the register state at `14000` matches a
  region deep inside the freeze window.
- **This casts real doubt on the existing 2026-07-22 "First visible
  original source geometry" TIMELINE.md milestone entry**, which was
  captured at `--post-poke-frames 14000` — past the start of this hang
  window. That capture's frame may not be live gameplay evidence at all; it
  needs **separate re-verification** (a fresh capture across a range of
  post-poke depths bracketing the hang, confirming which depths are live
  and which are frozen, and re-examining what that milestone's screenshot
  actually shows) before it can be trusted as anything more than "the
  emulator produced this specific frame of a specific bit-pattern in VDP1
  VRAM at that address at that instant" — the milestone's underlying visual
  gate claim (untextured/flat-shaded source geometry reached VDP1 at some
  point) is very likely still true given this session's own live 3600-depth
  data shows a real, if currently non-rendering, resolve pipeline, but the
  *specific screenshot* backing that milestone needs re-confirmation against
  a known-live depth.
- **Root-causing the hang itself was explicitly out of scope for this
