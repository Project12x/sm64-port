## What shipped this session

### The Fast3D-to-VDP1 lowering pipeline is real and wired end-to-end

```text
sourceboot/main.c's per-frame loop
  -> game_loop_one_iteration() (unmodified stock SM64 source)
     -> display_and_vsync() -> exec_display_list()
        -> sm64_saturn_fast3d_frontend_submit()   (decode + transform + cull + resolve)
  -> sm64_saturn_fast3d_vdp1_emit()               (depth-sorted VDP1 command emission)
     -> sm64_saturn_vdp1_backend_upload()
     -> vdp1_sync_render(); vdp1_sync();          (arms hardware sync, see below)
```

New/extended files:

- `src/port/saturn/gfx/saturn_matrix.h` — new. Q16.16 fixed-point 4x4 matrix
  type, decode (from the real `GBI_FLOATS` float source format this fork's
  `F3DEX_GBI_2E` build flag activates — **not** classic N64 s15.16, a wrong
  premise in the original design spec, corrected during implementation),
  overflow-guarded multiply, and an 11-deep modelview stack with lazy
  projection×modelview composition.
- `src/port/saturn/gfx/saturn_fast3d_frontend.{h,c}` — extended. Now decodes
  `G_MTX`, `G_POPMTX`, `G_MOVEMEM` (viewport), `G_GEOMETRYMODE`, `G_VTX`,
  `G_TRI1`, `G_TRI2`, and resolves each triangle through transform →
  backface-cull → near/far-and-span-reject → degenerate-reject →
  depth-bucket, into a bounded `resolved[]` array
  (`SM64_SATURN_FAST3D_MAX_RESOLVED_TRIANGLES = 192`).
- `src/port/saturn/gfx/saturn_vdp1_backend.h` — extended. Embedded
  `vdp1_cmdt_list_t` (was a heap pointer), `memalign`-backed heap init, and a
  new caller-storage init entry point for LWRAM-resident command buffers.
- `src/port/saturn/gfx/saturn_fast3d_vdp1_emit.{h,c}` — new. The only
  Yaul-dependent half of the pipeline; walks `resolved[]` far-to-near by
  depth bucket (painter's algorithm) and writes real VDP1 degenerate-quad
  polygon commands.
- `src/port/saturn/sourceboot/sourceboot-cart.x` — new `lwram` MEMORY region
  (`0x00200000`, 1 MiB, real Saturn LWRAM) and `.lwram_cmdts` output section
  for the VDP1 command staging array.
- `src/port/saturn/sourceboot/main.c` — wired: LWRAM-backed backend init at
  boot, `sm64_saturn_fast3d_vdp1_emit()` called once per frame after
  `game_loop_one_iteration()`.
- `tools/saturn/runtime_contract_test.c` — grew from 7 to 41 host-native
  tests (compiled and run under the host's own `$(CC)`, no Yaul toolchain
  needed — see `Makefile.saturn.mk`'s `verify-runtime-contracts`, now part of
  `verify-all`).

### Verified state

- `make -f Makefile.saturn.mk verify-all` passes: 59 Python tests, 41 native
  contract tests, `verify-hello`/`verify-hwtest` cross-compiled ELF checks.
- Full `sourceboot` cross-compile (`make source-assets && make && make
  verify`) passes: entry point `0x6004000`, `.cart_rodata` at `0x22400000`,
  cart image `1,694,864` bytes (within the 4 MiB budget).
- 6-mutation testing pass (per the project's global mutation-testing rule):
  0% survival — every mutation applied to the matrix/frontend math was
  caught by an existing test.
- A real hardware-timing bug was found and fixed during review: the initial
  per-frame wiring DMA'd a fresh VDP1 command table every frame with nothing
  confirming VDP1 had finished plotting the *previous* table first (a real
  tearing/corruption risk on actual hardware, traced against
  `third_party/libyaul`'s `vdp_sync.c` state machine). The fix
  (`vdp1_sync_render(); vdp1_sync();` after each frame's upload, without the
  full `castleviewer`-style blocking dance, which would have silently halved
  `sourceboot`'s game-loop rate by adding a second, redundant vblank wait)
  was independently adversarially re-reviewed and confirmed correct.

### HWRAM budget is now tight

The `ram` MEMORY region (`ORIGIN = 0x06004000, LENGTH = 0x000FC000`) has
**~380 bytes of margin** after this work, measured from the real linked ELF
(`___end` vs. the region's top). This is down from an earlier ~4,600-byte
estimate that only tracked one struct's data growth, not the `.text` code
this whole pipeline added afterward (`.text`/`.rodata`/`.data`/`.bss` all
share this one region — there is no separate code budget). **Any future
sourceboot change that adds HWRAM `.bss`/`.data`/`.text` should check this
margin first.** The two cheapest knobs to shrink if headroom is needed:
`SM64_SATURN_FAST3D_MAX_RESOLVED_TRIANGLES` and
`SM64_SATURN_FAST3D_MAX_VERTICES` (both in `saturn_fast3d_frontend.h`, 16
bytes/entry each) — do not touch `SOURCEBOOT_VDP1_COMMAND_CAPACITY`, which
lives in LWRAM with ~1 MiB free.

## Known limitations (deliberate scope boundaries, not bugs)

- **No texturing, no Gouraud shading.** Output is flat-shaded (vertex 0's
  color) and untextured. `G_TEXTURE`/`G_SETTIMG`/etc. are counted in
  profiling stats only, never consulted for rendering.
- **No polygon clipper.** VDP1 has no homogeneous clip stage; triangles
  crossing near/far or exceeding `SM64_SATURN_MAX_PROJECTED_SPAN` (640) are
  rejected wholesale rather than clipped.
- **Non-full-height viewports are unhandled.** Peach's ending cutscene,
  credits zoom, and the Goddard face screen use viewports the current
  letterbox math doesn't cover — gameplay-frame scope only for now.
- **LWRAM allocation is uncoordinated across binaries.** `sourceboot`'s new
  linker-tracked `.lwram_cmdts` region and `castleviewer`'s pre-existing raw
  pointer (`collision_pool.c`, `0x000C0000`) don't overlap today (separate
  binaries, never co-linked) but there is no single source of truth for
  LWRAM claims across this codebase's binaries.
- **`matrix_stack.depth`/`.overflowed` don't reset per frame** (unlike
  `resolved_count`, which does). Real SM64 display lists always balance
  `G_MTX_PUSH`/`G_POPMTX`, so this is a non-issue in normal operation; it
  would only matter if a list ever faulted or was truncated mid-processing
  before reaching its own pops. Not fixed: doing so naively broke several
  existing tests that seed matrix-stack state via direct API calls before a
  single `submit()`, standing in for "a command already ran" — a real fix
  needs those tests restructured to seed state via actual `G_MTX` commands
  instead, a separately-scoped change. See the comment at the top of
  `sm64_saturn_fast3d_frontend_submit` for the full reasoning.

## ADDENDUM (2026-07-21, later): critical hardware bug found by SGL doc study

A study of official Sega SGL SDK documentation
(`docs/saturn/SGL_REFERENCE_NOTES.md`) surfaced a hardware constraint that
invalidates part of this handoff's shipped design: **SCU DMA cannot access
WORKRAM-L (LWRAM)** — libyaul's own `scu/dma.h:32` says reading or writing
LWRAM via SCU DMA "locks up the machine," corroborated by two official Sega
documents. The merged pipeline stages VDP1 commands in LWRAM
(`sourceboot_vdp1_cmdts`) and uploads through Yaul's
`vdp1_sync_cmdt_list_put()`, which is an SCU DMA read from that address with
no fallback (verified in `vdp_sync.c`). **On real hardware, sourceboot as
merged would hang on its first rendered frame.**

Equally important for the capture plan above: **Ymir does not model this
restriction** (verified — its SCU DMA source path is an unrestricted bus
read, `libs/ymir-core/src/ymir/hw/scu/scu.cpp:720`), so an emulator capture
would show correct triangles while retail hardware locks up. Treat any Ymir
capture of the current build as pipeline-logic evidence only, never as
hardware-viability evidence, until the upload path is fixed.

Fix directions and a second, smaller finding (the frontend's screen
coordinate clamp uses int16 bounds, but VDP1's valid window is only
±2047 x / ±1023 y — values beyond it can wrap on hardware) are recorded in
`SGL_REFERENCE_NOTES.md` under "Critical code-facing findings." The upload
path fix should land before the visual gate is treated as anything more than
an emulator smoke test.

**UPDATE (same day): both fixes landed.** `263c3f3` replaces the upload for
the LWRAM-staged sourceboot target with a CPU longword copy plus
`vdp1_sync_force_put()` (compile-time flag `SM64_SATURN_VDP1_LWRAM_STAGING`;
HWRAM-staged targets keep the SCU path plus a runtime LWRAM assert), and
`bc351f7` tightens the coordinate clamp to the VDP1 window and hardens the
safety comments. Both passed an independent verification review (fresh
rebuilds of all buildable targets, symbol/section audits, a reconstructed
baseline link) and an adversarial review that traced `vdp_sync.c` end to end
and found no hole. Remaining hardware-only unknowns: the LWRAM/SCU-DMA
lockup premise itself and sustained CPU stores to VDP1 VRAM during plotting
— both need the eventual retail-hardware run. Two build-system traps
discovered during this work, worth knowing before trusting any build:
Yaul's build does not recompile TUs when only headers change, and object
files carry @-mangled path names (a plain `find -name foo.o` matches
nothing) — force-delete the mangled objects for edited TUs or a stale-object
relink will masquerade as a clean build. Also: the HWRAM `ram` region is now
so tight that a ~200-byte debug assert overflows the link by 16 bytes; the
capacity knobs (`SM64_SATURN_FAST3D_MAX_RESOLVED_TRIANGLES`/`MAX_VERTICES`)
are the designated relief valve.
